# Stash — Roadmap & Design Notes

## Status

**Phase 1 (MVP) — done.** Auth (JWT + first-admin bootstrap), locations/categories, item CRUD (quantity/photo/location/category/min-quantity/expiry/warranty), unified `Item`+`Barcode` model (self-issued QR / existing UPC-EAN / Matter pairing code all as one barcode type), continuous camera scan (`/scan`) with `POST /api/items/scan` upsert (match → quantity+1, unknown → external lookup + auto-create), single label PNG download, low-stock/expiring-soon dashboard, Docker Compose + Proxmox LXC deploy, backup/restore.

**Phase 2 — done.**
- External barcode lookup (Open Food Facts → UPCItemDB fallback, cached in `ProductLookupCache`).
- Bulk label sheet PDF printing (`POST /api/labels/sheet`, `pdfkit`, A4 3-column grid). Bundles a subsetted Noto Sans KR font (`apps/api/assets/fonts/`) because pdfkit's built-in fonts have no Hangul glyphs and item names rendered garbled without it.
- Dedicated stock movement history screen (`/history`, `GET /api/movements`) — filter by item/reason, item+user joined in, deep-linkable via `?itemId=` from the item detail page's "전체 보기" link.

**Phase 3 — done.**
- Expiry/warranty push notifications — done. VAPID keys stored in `Setting` (admin generates via a button on 외부 연동, same "no .env edit/restart" pattern as garage), `PushSubscription` model, `apps/api/src/lib/push.ts` (`sendPushToUser`/`sendPushToAllUsers` — Stash sends to *all* users since inventory is shared household-wide, unlike garage's per-vehicle access lists), `apps/api/src/jobs/expiryNotifications.ts` (cron `0 8 * * *`, looks `LOOKAHEAD_DAYS=3` ahead, marks `Item.expiryNotifiedAt`/`warrantyNotifiedAt` so each due date only notifies once — `items.ts`'s `PATCH` resets those flags to `null` whenever the corresponding date field is changed, otherwise editing a past-due date to a new future one would never notify again). `PushNotificationSettings` component embedded on `/backup`. `sw.js` got `push`/`notificationclick` handlers.
- Manual theme toggle — done. `lib/theme-context.tsx` (`ThemeProvider`/`useTheme`) persists to `localStorage` (`stash_theme`) and sets `data-theme` on `<html>`; `globals.css` gained `:root[data-theme="dark"|"light"]` blocks (attribute selector out-specificities the existing `@media (prefers-color-scheme: dark)` block, so explicit choice always wins, "시스템" just removes the attribute and lets the media query drive it). A blocking inline script in `layout.tsx`'s `<head>` applies the stored theme before first paint to avoid a flash of the wrong theme. `ThemeToggle` component (라이트/다크/시스템) embedded on `/backup`. Language toggle deferred until i18n itself lands (toggling between one language isn't meaningful yet).
- PWA offline shell — done. `sw.js` precaches all top-level shell routes (`/`, `/login`, `/scan`, `/items`, `/locations`, `/categories`, `/labels`, `/history`, `/backup`, `/offline`), and its fetch handler now falls back to a dedicated `/offline` page (instead of `/`) for uncached *navigations* only — non-navigation asset requests (JS/CSS chunks) fail through normally rather than resolving to an unrelated HTML page. `OfflineBanner` (window `online`/`offline` listeners) shows a persistent notice when offline. Found and fixed a real bug in the process: `AuthProvider.fetchMe()` had no error handling, so a network failure (e.g. actually offline) left the app stuck on "불러오는 중..." forever instead of rendering the cached shell — it now caches the last-known user in `localStorage` (`stash_cached_user`) and falls back to it on fetch failure, only clearing on an explicit 401.
- ko/en i18n — done. `apps/web/lib/i18n/translations.ts` (flat key → `{ko, en}` dictionary, ~140 keys) + `lib/i18n/locale-context.tsx` (`LocaleProvider`/`useLocale`, persists to `localStorage` as `stash_locale`, `t(key, params?)` with `{param}` interpolation, `formatDateTime(iso)` using `Intl`/`toLocaleString` keyed off the *app's* selected language rather than the browser's, so switching in-app language also re-formats timestamps). `LanguageToggle` (한국어/English) embedded on `/backup` next to the theme toggle. Every page and component was migrated off hardcoded Korean strings — verified by grepping the whole `apps/web` tree for Hangul outside `lib/i18n/`, which now only turns up Korean *code comments* (intentionally left, matches the rest of the codebase's comment convention) and two data-driven exceptions that are correct to leave alone: actual user-entered content (names, item names) and `packages/shared` API error message strings (`apps/api` itself is not localized — only the `apps/web` UI layer is; a future pass could add an `Accept-Language`-aware error layer if needed). `apiJson()`'s fallback error message reads `stash_locale` directly from `localStorage` since it's a plain lib function outside any component tree.
- Push notification body text localization — done (follow-up after the initial i18n pass). `apps/api/src/lib/push.ts` gained `sendLocalizedPushToUser`/`sendLocalizedPushToAllUsers`, which take a `(locale: string) => PushPayload` builder and apply it per-subscription using each `PushSubscription.locale` (captured at subscribe time) rather than one fixed payload for everyone — additive, the original `sendPushToUser`/`sendPushToAllUsers` are untouched so `routes/push.ts`'s `/test` route didn't need changes. `expiryNotifications.ts`'s `formatDday` now takes a `locale` param (defaults to `"ko"`) and a small `MESSAGES.ko`/`MESSAGES.en` dict supplies the title/body templates. Verified end-to-end against the real Docker stack: created two real `PushSubscription` rows (one `ko`, one `en`, different users) and ran the job directly — logs confirmed both were processed independently through `sendLocalizedPushToAllUsers` → `sendLocalizedPushToUser`, with payload-building succeeding for both before failing at the (expected, since the test rows used fake encryption keys) `web-push` encryption step.

**Inventory event webhook — done.** Generic outbound webhook for webhook-capable printer/label-device automations (e.g. Home Assistant). Not named after any specific product in code or UI — see below.

## Bug/behavior verification pass (done)

Found and fixed while exercising every route against the real Docker+Caddy stack (not just the happy path):

- **Duplicate barcode value** attach/create crashed with a raw Prisma 500 instead of a clean error. Also surfaced a schema bug: `Barcode` uniqueness was scoped `[itemId, value]`, but `/scan`'s lookup (`findFirst({ where: { value } })`) assumes values are globally unique — two items could otherwise silently share a barcode with ambiguous scan matching. Changed to `@@unique([value])` (migration `20260711114634_barcode_value_globally_unique`), added `isUniqueConstraintError()` (`apps/api/src/lib/prismaErrors.ts`) used by both the manual-attach route (checked before insert, so a conflict never leaves an orphaned item behind) and `/scan`'s create path (self-heals a same-barcode race into a quantity bump instead of erroring).
- **Corrupted/invalid image upload** to `/api/attachments` crashed with a raw 500 (sharp's error message leaking to the client) instead of a 400. Now caught and returns a clean validation error.
- **Attachment files were never deleted from disk** — `DELETE /api/attachments/:id` only removed the DB row, and deleting an item (which cascades attachments at the DB level) didn't touch their files either, leaking the uploads volume forever. Added `deleteUploadedFile()` (`apps/api/src/lib/uploads.ts`), used by both paths.
- **Several frontend mutation handlers had no try/catch** (`addManualBarcode`, `addMatterBarcode`, `adjustQuantity`, `updateField`, `generateQr`, `removeBarcode`, `handleDelete` on the item page; location/category create; user delete; all four settings-page handlers) — a failed request just silently did nothing with no toast, only a console error. All now catch and surface `err.message`.
- **Error toasts showed literal escaped quotes** (`"메시지"` instead of `메시지`) for any string `error` field, because `apiJson()` always `JSON.stringify`'d `body.error` regardless of whether it was already a string (only Zod validation failures are objects). Fixed to pass strings through as-is.

Verified via the actual `docker compose` + Caddy stack (not just `npm run dev`): categories CRUD, role-based 403 on admin routes, quantity floor at 0, location deletion `SetNull`s (doesn't delete) attached items, and a full backup export → restore round-trip.

## Inventory event webhook (implemented)

Admin sets one URL (`INVENTORY_WEBHOOK_URL`, Settings → 외부 연동 → "재고 이벤트 웹훅"; same `Setting` table pattern as `UPCITEMDB_API_KEY`, excluded from backup). Stash POSTs a JSON payload to it in two cases, built by `buildWebhookPayload()` in `apps/api/src/lib/webhook.ts`:

- `item.updated` — fired automatically whenever an item is created, edited, quantity-adjusted, or matched/created via `/scan` (`apps/api/src/routes/items.ts`). Fire-and-forget, not awaited, never blocks the request.
- `item.print_requested` — explicit "프린터로 출력" action (`POST /api/items/:id/print-request`), available on the item detail page and as a bulk action on `/labels`. Returns 400 with a clear error if no webhook is configured or the item has no barcode.

Payload shape: `{ event, itemId, name, quantity, unit, locationId, locationName, barcodeValue, symbology, labelImageUrl, timestamp }`. `barcodeValue`/`symbology` alone are enough for the receiving automation to render its own barcode — `labelImageUrl` (pointing at `GET /api/barcodes/:id/label.png`) is sent as a convenience only, not required. That endpoint was made **intentionally unauthenticated** (moved to `publicBarcodeRoutes` in `barcodes.ts`, registered separately in `index.ts`) so external automations can fetch it without a token; barcode ids are unguessable cuids, so this was treated as an auth-relaxation decision requiring explicit user sign-off (given) rather than something to decide unilaterally — worth remembering if this endpoint is touched again.

UI copy is deliberately generic ("재고 이벤트 웹훅", "웹훅을 받을 수 있는 프린터·라벨 기기 자동화") rather than naming specific integrations, since any webhook-triggered automation can consume this — not just the two below. The settings page has a "전송되는 데이터 보기" `<details>` block listing every payload field for whoever is building the receiving automation.

**Context on why this exists** (kept for reference, not required reading to use the feature): the repo owner's own Home Assistant custom components `hass-niimbot` (BLE thermal printer, one-shot print) and `hass-gicisky` (BLE e-paper shelf label, persistent — needs refreshing on every data change, which is why `item.updated` fires on every change rather than only on an explicit action) both expose their print service as HA's declarative **imagespec** element format over `POST /api/services/<domain>/<service>`. Stash deliberately doesn't speak imagespec or know about `device_id`/HA tokens — that's entirely the receiving automation's job, filtering incoming webhook events by `itemId` per physical device if needed.

Tests: `apps/api/src/lib/webhook.test.ts` covers `buildWebhookPayload`/`buildLabelImageUrl`/`signWebhookBody` (primary-barcode selection, no-barcode case, URL construction, HMAC) without hitting the network or DB. `apps/api/src/lib/barcodeSymbology.test.ts` covers `guessSymbology`. Going forward, add a `*.test.ts` next to new pure/extractable logic as it's written — established as the ongoing convention for this project, not a one-off. `apps/web` has `vitest.config.ts` for unit tests where needed.

## Security hardening (implemented)

Decisions and tradeoffs for the hardening pass (ordered by impact):

- **Attachment file serving auth (P0).** `<img src>` cannot send `Authorization`, so a dedicated httpOnly `stash_media` cookie (24h, `purpose: "media"`, path `/api/attachments/file`) is set on login **and refreshed on every `/api/auth/me`** (AuthProvider mount + `visibilitychange` when the tab becomes visible) so photos don't die after 24h while the 7d JWT is still valid. Cookie **or** Bearer is required unless `MEDIA_AUTH_DISABLED=true` (explicit opt-in for cross-origin local `npm run dev`; commented out in `.env.example` so copying the template cannot silently disable prod auth if someone later adds `env_file: .env`; logs a startup warning). `authenticate` rejects `purpose:"media"` so the cookie value cannot be reused as a full API Bearer. **Residual risk:** logout / logout-all / password change / admin `reset-password` bump or clear client state for Bearer, but a media token already in another browser (or left after admin reset of that user) is **not** tied to `tokenVersion` and stays valid until its 24h expiry — exposure is limited to attachment reads. Barcode `label.png` stays intentionally public (automation fetch). PDF responses force `Content-Disposition: attachment` + `X-Content-Type-Options: nosniff`. HTTPS installs set `COOKIE_SECURE=true` (passed through compose into the api container).
- **No query-string JWT (P0).** Removed general `?token=` fallback from `authenticate`. CSV export still uses `apiFetch` + blob. **Backup export** uses a separate 60s one-time `purpose:"backup"` ticket (`POST /export-ticket` → `GET /export?ticket=`) so the browser can stream large tarballs without loading them into JS memory; `authenticate` rejects `purpose:"backup"` the same way as media. Logger redacts `ticket` as well as `token`/`sig`.
- **Role re-check + token invalidation (P0).** `requireAdmin` always re-reads `role` from DB (admin routes are infrequent; demotion must apply immediately). `User.tokenVersion` + JWT `tv` claim (**required** — missing `tv` → 401, so pre-upgrade 90d tokens die on deploy); migration bumps existing rows to `tokenVersion=1`. Password change and **logout-all** bump the version; default logout does not (see Phase 2). `authenticate` compares `tv` via a **60s in-memory cache** so continuous scan is not hit with a DB round-trip every time — invalidation can lag up to 60s. JWT lifetime shortened 90d → **7d**.
- **JWT_SECRET required in production (P0).** Empty / `changeme` / `dev-secret-change-me` → `process.exit(1)`. Dev keeps warn + fallback. CORS stays `origin: true` for now (Bearer + dev cross-origin + webhook receivers); documenting rather than tightening prematurely.
- **Postgres not published on the host in prod (P0).** Removed `ports:` from `docker-compose.prod.yml` and the Proxmox-generated compose. Dev compose binds `127.0.0.1:${POSTGRES_PORT:-5433}:5432`.
- **CSV formula injection (P1).** Leading `=+-@\t\r` on string fields get a leading `'`; numeric columns stay untouched. Import strips the guard for round-trip.
- **Backup omits passwordHash (P1).** Restore fills random hashes and returns one-time passwords for **all** users without a hash. Legacy backups that still include hashes restore as before. (Admin can also reset a living user's password via Phase 2 `reset-password` without deleting the account.)
- **Webhook HMAC (P1).** Optional `INVENTORY_WEBHOOK_SECRET` → `X-Stash-Timestamp` + `X-Stash-Signature: sha256=<hex>` over `"<ts>.<raw body>"`. Unset = previous unsigned behavior. Delivery retries up to 3 times (0 / 1s / 4s) for 5xx and network/timeout only — not 4xx. Still fire-and-forget from CRUD; in-memory only so process restart drops in-flight retries. Each attempt re-signs with a fresh timestamp.
- **Relative photoUrl (P2).** Stored as `/api/attachments/file/<file>`; migration strips host prefixes. Rendering prepends `API_URL`. Avoids domain-change breakage and keeps cookie auth compatible with existing rows.
- **Dependabot + `npm audit` in CI (P2).** CI runs `npm audit --omit=dev --audit-level=high` (production tree only — toolchain advisories must not block unrelated PRs). Stack: Fastify 5 / `@fastify/jwt` 10 / `@fastify/cors` 11 / Next.js 16 / React 19 / Prisma 7 (`prisma.config.ts` + `@prisma/adapter-pg`) / TypeScript 7 / sharp 0.35. ESLint uses the flat config CLI (`eslint .`) because `next lint` was removed in Next 16. TS 7 requires explicit `rootDir` on api/shared `tsc` projects. `prisma.config.ts` allows a localhost dummy `DATABASE_URL` **only for `prisma generate`**; migrate/deploy throw if the env is missing so a misconfigured prod install cannot silently aim at localhost. **npm Dependabot ignores all `semver-major`** — majors are absorbed in one manual PR (as with #26–#30 → #34); weekly PRs stay grouped minor/patch only. Docker still ignores `node` majors only (LTS policy).
- **Node.js LTS alignment.** Dockerfiles and CI use **Node 24** (even-numbered LTS). Dependabot's docker ecosystem does not distinguish LTS vs Current, so both Docker entries ignore `node` **semver-major** — LTS jumps stay manual; minor/patch security bumps still auto-open. **Next manual check:** when Node 24 enters Maintenance LTS (scheduled ~2027-10 per Node release schedule), evaluate bumping Docker/CI to the then-Active LTS (likely 26). Tracked in [#32](https://github.com/eigger/stash/issues/32).
- **`react-hooks/set-state-in-effect` off (temporary).** Next 16's eslint-plugin-react-hooks forbids `setState` inside `useEffect`. The app uses that pattern widely for auth hydration, list refresh, and localStorage reads. Enabling the rule would be a broad client-data refactor, not an audit fix — disabled in `eslint.config.mjs` until that work is scheduled. Tracked in [#31](https://github.com/eigger/stash/issues/31).

## Phase 2 — practical UX (in progress)

- **Admin password reset (not reveal).** `POST /api/auth/users/:id/reset-password` issues a server-chosen one-time password (`randomBytes(12).toString("base64url")`), hashes it, bumps `tokenVersion`, and returns the plaintext once. Admins cannot set or look up another user's password — that would blur "temporary" and enlarge impersonation risk. Self-reset is rejected (use `/profile`). StockMovement / createdBy history stays intact because the user row is not deleted.
- **One-time secrets UI.** Restore recovery passwords and admin resets share `OneTimeSecrets`: copy / copy-all / `.txt` download, selectable text for HTTP (no Clipboard API), and a "I saved these" checkbox before dismiss. Replaces `window.alert`, which is uncopyable on iOS Safari and easy to dismiss permanently.
- **Logout vs logout-all.** Default `POST /logout` clears the media cookie only (this device). `POST /logout-all` bumps `tokenVersion` for every device. Password change still always bumps. **Tradeoff:** after a normal logout a stolen Bearer can remain valid up to 7d — "log out everywhere" is offered prominently in Settings instead of making every logout wipe the kitchen tablet.
- **Label deep-link / bundle.** `/i/[id]` is a server `redirect()` to `/items/[id]` (no client runtime for the hop). Item detail/new never statically import `@zxing/*` — `createScanHints()` + `import("@zxing/browser")` run only when the add-barcode scanner opens; `symbologyFromScanFormat` / `isQrScanFormat` use numeric format constants guarded by `barcodeScanner.test.ts` against `@zxing/library` enums. `/scan` keeps eager zxing. **Measured** (`npm run measure:zxing` after web build): detail/new manifests do not mention library/browser; scan pulls the ~443 KB `@zxing/library` chunk (~563 KB page total). The script's `zxingInThoseKB` is a substring upper bound (see script comment), not exact decoder bytes.
- **Backup export ticket.** Admin gets a 60s JWT (`purpose:"backup"`, `jti`) then opens `/api/backup/export?ticket=…` in a new tab (`target="_blank"`) for `createReadStream` delivery so a failed ticket does not replace the SPA. Consumed jtis live in process memory and are deleted after 60s; multi-instance still does not share the set.

## Phase 3 — management persistence / gamification (in progress)

Hypothesis (not a confirmed defect): people abandon inventory when drift can't be fixed quickly, and when careful entry feels the same as sloppy entry. Rewards are layered so they don't Goodhart each other:

| Layer | When | Rewards | Failure it blocks |
|-------|------|---------|-------------------|
| 1 Quality XP | On entry | Field completeness (useful fields weighted) | Sloppy input |
| 2 Confirm XP | On later verification | Accuracy (found at recorded location / qty match) | Filling garbage for points |
| 3 Freshness | Continuous decay | Trust state of stock | Neglect / drift |

**Order:** A → B → *(pause ≥3 weeks)* → C → D. Do not ship C/D before living with A+B.

### P1-A — location audit mode (this PR)

- **Why first:** without a way to correct a whole shelf in minutes, freshness (B) only shows guilt. Game-wise it's a session with clear start/end/progress.
- **Model:** `AuditSession` + `AuditCheck` (PENDING/FOUND/UNEXPECTED). One ACTIVE session per household; persisted so closing the app doesn't corrupt confirmed fixes. **Not** in backup/restore — ephemeral work state; items/locations already are.
- **API:** `POST/GET /api/audit/sessions`, `…/scan`, `…/confirm`, `…/register`, `…/finish`, `…/cancel`. Scan confirms presence (does not +/- stock). Quantity fixes use `StockMovement` `ADJUST`. Finish asks what to do with unscanned rows (`ZERO` / `MOVE` / `LEAVE`) — **never auto-delete**. Finish runs in **one `$transaction`** after a pre-flight plan (`buildFinishPlans` + zod `superRefine`) so a bad MOVE exception cannot leave half the shelf zeroed. Soft-deleted items are not resurrected on finish/confirm (unlike `/scan`, which intentionally undeletes).
- **UI:** `/audit` + `/audit/[sessionId]`; reuses `createScanHints()` / scanner chrome from `/scan`. Online-only for v1 (session is stateful; offline queue has no location/mode metadata). Active session payload includes `startedBy` so a 409/resume card can show who started it (still household-wide co-op — anyone may finish).
- **`lastAuditedAt`:** already updated on `/scan`; now also when `PATCH`/`POST …/quantity` actually changes quantity (manual confirm counts as an audit).
- **Webhooks:** finish fires `item.updated` for ZERO/MOVE results (shelf labels must not keep stale qty), drained **sequentially in the background** so a 100-item finish does not open 100 concurrent fetches. Confirm still fires per item as the user scans.
- **Anti-patterns deferred:** streaks, leaderboards, badges/levels, lossy push nags — see workorder §2.2–2.3 (“useful with game stripped off”).

### P2-B — freshness / inventory trust (this PR)

- **Pure helpers** in `@stash/shared` (`freshness.ts`): CONSUMABLE **30d** / ASSET **365d** thresholds (commented why — tools must not go red in a month). Ratio = trusted items / all non-deleted. Confirm time is `lastAuditedAt ?? createdAt` so a cold deploy does not open at ~0% (“registration is a check”). Continuous decay (items cross the threshold one by one) — no streak cliff. Tests live in `apps/api` importing `@stash/shared` (same pattern as other shared pure logic).
- **API:** `GET /api/items/stats` adds `freshness`; `GET /api/locations` attaches per-location `freshness` including **descendant** locations (`collectLocationIds`) so a room is not “empty” when only shelves hold items.
- **UI:** dashboard trust card (“창고가 흐려졌다” tone, link to `/audit`); location tree dots + percent. No freshness push (v1). Expiry warnings stay on the existing system — not duplicated here.
- **Pause:** live with A+B ≥3 weeks before C/D (workorder §5).

**Next:** Phase 3 management loop complete (A–D). Field-validation issue [#39](https://github.com/eigger/stash/issues/39) remains useful for judging whether C/D help or mask input-path problems.

### P3-C — quality + confirm XP (this PR)

- **Quality (layer 1):** derived — `sumQualityXp` over current non-deleted items. Not accumulated in Setting, so empty→fill farming and backup restore both stay consistent (score follows item state). Toast may still show a per-action delta via `computeQualityXp(item, previous)` without writing DB.
- **Confirm (layer 2):** cumulative in `Setting` key `HOUSEHOLD_CONFIRM_XP`, incremented with a single SQL `INSERT … ON CONFLICT DO UPDATE` so concurrent audit/scan grants cannot drop updates. Awarded only on audit PENDING→FOUND. **Backup/restore resets confirm XP to 0** — `Setting` is excluded from backups (secrets), and `AuditSession` is also excluded (ephemeral work state), so there is no safe way to rebuild the counter; quality XP still reappears from restored items.
- **Display:** `GET /api/xp` → `{ quality, confirm, total }` (quality is recomputed from all live items + barcodes each request — fine at household scale; if the dashboard ever feels slow, fold this into `/api/items/stats` so the same rows are not scanned twice). No shop/levels/leaderboard. No historical backfill of confirm XP.
- **Hooks:** create/PATCH/scan return quality toast payload only; scan match path still grants nothing (anti-pattern: scan-count rewards).

### P3-D — retrospectives / insights (this PR)

- **Why:** reward the labor of keeping stock with facts, not badges (§2.3). Built only from `StockMovement` + `Item.price`/`purchaseDate`/`lastAuditedAt`/`createdAt` — no new tables.
- **Pure helpers** in `@stash/shared` (`insights.ts`): untouched (≥365d via `lastAuditedAt ?? createdAt`, always “as of now” — not tied to the month pager), top CONSUME this month, duplicate RESTOCK on **≥2 distinct UTC days** (same-day continuous scans count as one trip), purchased-in-range (`purchaseDate ?? createdAt`) with unit-price `totalByCurrency` over **all** matching items (list may be capped). Month bounds come from the client as ISO `from`/`to` (local calendar) so the server never guesses timezone.
- **API:** `GET /api/insights?from=&to=` (max ~3 months). Soft-deleted items excluded; ADJUST never counts as consume/purchase.
- **UI:** `/insights` (month pager) + dashboard link + More menu. Copy is factual only — no “waste” sermons. Unit-price total is labeled distinctly from dashboard inventory value (`price × quantity`). `purchaseDate` still has no form field; totals fall back to registration date (documented in the hint).
- **Out of scope:** judgmental copy, XP shop, purchaseDate form (separate if needed).
